# Proposal: add-notification-contracts

## Why

Ratatoskr's legacy monolith notified users in-process; the fleet cannot. `ratatoskr-knowledge`, `ratatoskr-github`, `ratatoskr-vault` and `ratatoskr-x` need a wire contract with which they can tell the fleet that a user should be told something, without importing Telegram types, and `ratatoskr-telegram`'s notification sender (its plan item 10) needs that same documented bus surface to consume. Today no such contract exists, so every producer would invent its own notification shape or drop user-facing signals entirely.

## What Changes

- Add a new contract crate `crates/notification-contracts` (`ratatoskr-notification-contracts`) defining the typed payload of one registered event type, `platform.notification.raised.v1`, carried inside the canonical event envelope.
- Define a versioned, extensible notification-class taxonomy (`NotificationClass`): six known classes at registry version 1 — `operation_completed`, `operation_failed`, `analysis_ready`, `backup_outcome`, `watch_triggered`, `archive_imported` — with unknown class tokens readable-and-preserved (`Other(String)`), never rejected.
- Address recipients through the existing tenancy grammar (`recipient: TenantRef`, closed to `user:<uuid>`); carry correlation references as opaque open-vocabulary references (`operation_ref`, `analysis_ref` as `EntityRef`).
- Carry advisory delivery hints — `priority_hint` and `quiet_hours` (a daily UTC offset window) — whose enforcement stays in `ratatoskr-telegram`; the contract fixes only their wire shape.
- Register the contract in `contracts.toml` (family `events`, owner `ratatoskr-platform`, producers knowledge/github/vault/x, consumer ratatoskr-telegram), extend the closed `[services]` vocabulary with `ratatoskr-telegram` and the fixture `[entity_kinds]` vocabulary with `notification` and `analysis`.
- Add `NotificationId` to `ratatoskr-identifiers` (typed UUID identity of one raised notification; also the aggregate kind `notification:`).
- Add valid fixtures per class (including an unknown-class preservation fixture), invalid fixtures with `invalid-expectations.toml` rows, regenerated JSON Schema + TypeScript artifacts, and frozen public-API baselines for the touched crates.

Explicit non-goals: delivery guarantees beyond the bus's own at-least-once semantics (Telegram owns dedupe and preference filtering); email/webhook delivery channels (unassigned backlog); preference storage (Telegram's schema); UI rendering.

## Capabilities

### New Capabilities

- `notification-contracts`: the wire agreement through which producer services raise typed user-facing notifications onto the documented bus surface `ratatoskr-telegram`'s notification sender consumes: the class taxonomy with registry versioning, tenant/user addressing, opaque correlation references, advisory priority/quiet-hours hints, and envelope alignment for `platform.notification.raised.v1`.

### Modified Capabilities

(none — no existing spec covers notifications)

## Impact

- New crate `crates/notification-contracts` added to the workspace; new dependency edges on `ratatoskr-identifiers` and `ratatoskr-event-envelope`.
- `crates/identifiers` gains one public type (`NotificationId`) — additive, but the compatibility job diffs against frozen baselines, so `compat/api/ratatoskr-identifiers.txt` is re-blessed and a baseline for the new crate is created via `cargo contracts api-write`.
- `contracts.toml`: one new `[[contract]]` row plus two vocabulary extensions (`ratatoskr-telegram`, `notification`, `analysis`).
- Generated trees gain `schemas/events/platform.notification.raised.v1.schema.json` and `generated/typescript/events/platform.notification.raised.v1.ts` (regenerated by `cargo contracts generate`, never hand-edited).
- Docs updated where they enumerate crates, families and event types: `README.md`, `DEVELOPMENT.md`, `AGENTS.md`.
