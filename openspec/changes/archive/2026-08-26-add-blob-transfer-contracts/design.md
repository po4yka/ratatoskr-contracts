# Design: add-blob-transfer-contracts

D1. **Documents, not commands or events.** The generator pipeline emits two families today: JSON-Schema documents and `family = "events"` payloads; command envelopes have no pipeline support. Session initiation and finalize are modeled as request/receipt documents over the canonical HTTP binding (platform ADR-0015 `transfer` class), not as bus commands. No event is added — the transfer's completed fact is the receiving service's own stored blob, addressable per the workspace store spec `blob-references`; announcing it is that service's existing business, not this protocol's.

D2. **Six contracts, one root each, split by emission direction.** The fixture harness and metadata rule R3 both bind a `fixtures_dir` and one generated artifact to a contract's single canonical root, so the grain of governance is the message shape, not the protocol family. Client-to-receiver shapes: `transfer.upload_session_request`, `transfer.upload_finalize_request`. Receiver-to-client shapes: `transfer.upload_session_opened`, `transfer.upload_chunk_receipt`, `transfer.upload_status_response`, `transfer.upload_completion_outcome`. Direction is expressed through each block's producers and consumers. Owner is `ratatoskr-platform` as steward of a fleet-wide protocol whose storage ownership stays with receivers.

D3. **Chunk index, not byte range — decided once.** Index addressing against a declared fixed chunk size gives every participant the same deterministic arithmetic from the declaration alone: idempotent replay keys on `(token, index)`, resume state is an exact integer set, divergence detection compares one recorded digest per index, and out-of-range/gap rules are total functions. Byte ranges would force servers to reconcile overlapping or misaligned ranges, make "same bytes twice" ambiguous, and buy parallelism v1 does not use. Any-order delivery within the derived count remains legal; ordering discipline is the client's choice, completeness is checked only at finalize.

D4. **Digest-first with SHA-256 fixed at version 1.** The declaration carries the whole-payload digest before any byte moves, so a receiver can refuse early on size/media/digest metadata. Algorithm negotiation would be dead weight while exactly one algorithm exists: the field is a closed single-variant vocabulary (`sha256`) so a future algorithm arrives as an additive enum variant plus a registry-version bump, not as a stringly-typed escape hatch.

D5. **Tokens are opaque and grammar-bounded.** `UploadResumptionToken` validates shape only (`rst_` + 24–64 lowercase base32-ish characters); entropy, issuance and expiry are server obligations the contract states in prose. Distinguishing unknown-token from expired-token failures lets clients re-open cleanly instead of retrying forever.

D6. **Mismatch is an outcome, not an envelope error.** Finalize always answers with `UploadCompletionOutcome`: `stored` — carrying the complete `BlobRef` (owner service, digest, media type, length), everything the workspace store spec `blob-references` requires to resolve the bytes — or `digest_mismatch` carrying expected and computed hex. A mismatch is an anticipated terminal fact about the bytes, truthfully recorded in session state; envelope errors are reserved for the unanticipated (unknown/expired token, conflict, premature finalize, malformed messages). Codes live in `TransferErrorCode`, mapped onto `error_contracts::ErrorCode` (`2–4` dot segments under `blob_transfer.`), each with an explicit retriable flag.

D7. **A transport-free reference state machine ships with the types.** `chunks` (total addressing arithmetic) and the session transition model encode the normative semantics so the acceptance tests — transitions, resume sequences, digest-mismatch finalization, idempotent replay — run against the same rules every implementer reads. This is protocol definition, not business logic: no storage, no I/O, no clocks beyond explicit instants in messages.

D8. **Bounds are constants of the protocol, not configuration.** Minimum/maximum chunk size and maximum chunk count are named constants in the crate (documented in the type docs); they bound status answers and memory behavior for every implementation. Changing one is a review-visible contract edit, which is exactly the weight a wire limit should have.

D9. **Registry footprint.** Six new roots → registry pins move 20→26 (artifacts 40→52, TypeScript pins likewise); `[services].known` gains `ratatoskr-mobile` and `ratatoskr-export-agent`; `[lint].timestamp_property_names` gains `expires_at`. No entity-kind additions: these documents carry no aggregate references. Privacy classification is `user_content` on both contracts; `unknown_policy` stays `preserve`.

D10. **Canonical HTTP binding, documented not encoded.** `lib.rs` and the architecture section fix the mapping: `POST /v1/<svc>/uploads` opens; `PUT /v1/<svc>/uploads/{token}/chunks/{index}` delivers raw chunk bytes with `Content-Length` equal to the expected length; `GET .../status` resumes; `POST .../finalize` completes. Status usage: receipts 200, opened 201, outcome 200 (both variants), incomplete/conflict/token failures as envelope faults. Types carry none of this.
