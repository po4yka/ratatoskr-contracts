# ADR-0001: Canonical schema source format

> Status: Accepted  
> Last reviewed: 2026-08-18

## Context

Every contract in this repository must exist in Rust, because the services are written in Rust, and in JSON Schema, because validation, and later TypeScript, Kotlin and Swift, need a language-neutral form.

`ARCHITECTURE.md` S4 and S15.2 require exactly one canonical source per contract. `AGENTS.md` forbids two hand-edited authoritative copies. Nothing has been generated or published yet, so this is the initial decision and there is no migration to plan.

## Drivers

1. One canonical source per contract (`ARCHITECTURE.md` S15.2).
2. Deterministic, reproducible generation with a clean-tree drift check (`ARCHITECTURE.md` S11).
3. Identifier string formats that are "stable and **validated**" (S5.1) — validated at construction, not only described in prose.
4. Cross-field and canonical-form invariants that JSON Schema draft 2020-12 cannot express: the envelope version gate, the operation snapshot invariants I1–I5, and the rule that one instant has exactly one spelling.
5. No hand-maintained duplicate definitions (`ARCHITECTURE.md` S4, `AGENTS.md`).
6. `AGENTS.md` design principle 1: every serialized field must be documented.

## Options

### Option A — Rust-first (chosen)

`#[derive(JsonSchema)]`, plus hand-written `JsonSchema` implementations for the validated newtypes. `contractsc` renders `schemas/**` from the Rust types.

For:

- It is the direction the named toolchain runs in.
- A doc comment becomes the schema `description`, so `#![deny(missing_docs)]` enforces driver 6 mechanically instead of by review.
- The published `pattern` and the runtime validator are the same `const`, so the two cannot drift.
- Invariants live in `Deserialize`, so an invalid value is unrepresentable and not merely undocumented.
- One language to review, and `cargo` alone runs everything.

Against:

- Consumers that are not written in Rust depend on generated artifacts until milestone 8.
- A `schemars` upgrade can change every artifact.

### Option B — JSON Schema first

Hand-authored schemas, with Rust generated by `typify` or a comparable tool.

Against:

- No schema-to-Rust tool appears anywhere in the repository documentation, while `DEVELOPMENT.md` names exactly one code-generation crate and that crate runs Rust to Schema.
- Generated Rust cannot host driver 3 or driver 4, so a second hand-written validation layer would be necessary. That is the two-authorities problem under another name.
- Doc comments would have to be copied into `description` by hand.
- Reviewers would read generated Rust instead of the contract.

### Option C — both hand-maintained

Forbidden outright by `AGENTS.md`.

## Decision

Option A. The canonical source of the shape of every milestone 1–4 contract is the Rust type in `crates/*/src/**.rs`. `schemas/**` is generated, carries an `x-ratatoskr-provenance` member, and is never hand-edited (`ARCHITECTURE.md` S15.3).

**The citation that settles it.** `DEVELOPMENT.md`, "Intended toolchain": *"Rust, Serde, **Schemars**, JSON Schema, OpenAPI, deterministic generators, and generated Rust/TypeScript packages."* Schemars exists for one direction only — it derives JSON Schema *from* Rust — so naming it names the direction. A schema-first repository would list `typify` or `quicktype`, and would have no use for Schemars. `ARCHITECTURE.md` S4 row 1 says the same thing: "Rust-first value types | Rust type plus generated JSON Schema".

**The one apparent counter-citation, addressed.** S4 row 3 reads "Event payloads | Versioned JSON Schema and matching Rust type". That row is satisfied, not violated: a versioned JSON Schema exists and a matching Rust type exists. The row names a *pair* of artifacts, not an owner. S4's own opening line ("Every contract has one canonical source") means one of the pair must be derived, and the row does not say which. The only reading the decision excludes is "both hand-authored", which `AGENTS.md` already bans. "Matching" is a property `cargo contracts check` guarantees, not one a person maintains.

**The canonical rendering is decided here too**, because a canonical source format means nothing without one:

- JSON Schema draft 2020-12.
- `$id` is a URN: `urn:ratatoskr:contracts:{family}:v{major}:{Type}`.
- Two-space pretty printing, exactly one trailing `\n`, UTF-8 without a BOM, LF line endings.
- `required` arrays are sorted lexicographically, so a Rust field reorder is a schema no-op.
- No floating-point number appears in any schema or in any fixture that is meant to be accepted.
- The `preserve_order` feature of `serde_json` must never be enabled anywhere in the workspace.
- `source_digest` is a SHA-256 taken over the rendered schema body **with the provenance member removed**. `ARCHITECTURE.md` S11 says "source digest" but does not say a digest of what. A provenance-free digest makes a generator-version bump change one line per file and no digest, so a moved digest always means a real contract change.

## Consequences

- **The JSON Schema is a lower bound on validity.** It accepts payloads that the Rust type rejects: the cross-field invariants and the one-spelling-per-instant rule. Every generated file states this in its `validation_note`, and it is why every invalid fixture declares in `fixtures/invalid-expectations.toml` which layer must reject it. This is not a defect to be hidden by generating unreadable `allOf`/`if-then` blocks.
- Consumers that are not written in Rust get the schema, not the invariants, until milestone 8 generates typed clients. This is a known gap, recorded here.
- A `schemars` upgrade is a repository-wide regenerate-and-review event. It gets its own PR, the whole diff is reviewed, and the changeset records it. The `schemars_version` member of the provenance block records which version produced the bytes. This is not automatable and must not be automated.
- A contributor who knows only JSON Schema cannot add a contract without writing Rust.
- **OpenAPI is explicitly not decided by this ADR.** `ARCHITECTURE.md` S4 gives OpenAPI a different canonical source ("generated from Platform routes or contract definitions"). A follow-up ADR at milestone 8 decides it.

## Security / privacy

All schema text comes from reviewed Rust doc comments, and `serde_json` escapes it on the way out. That is the mitigation `THREAT_MODEL.md` asks for under "Malicious schema text/codegen injection".

The `privacy` enumeration in `contracts.toml` has no `credential` variant, so a credential-bearing contract cannot be declared at all: such a file fails to parse. This is the `SECURITY.md` baseline enforced at the type level.

Fixtures are synthetic, every fixture UUID comes from one reserved block, and every byte under `fixtures/**` is scanned for credentials, personal data, storage paths and URLs by `cargo contracts check`.

## Compatibility / migration

There are no existing artifacts and nothing is published, so there is nothing to migrate.

Superseding this ADR would require regenerating every artifact and re-reviewing every contract. Record a superseding ADR; do not edit this one.

## Validation

Test identifiers refer to the test matrix in the implementation specification:

- G-1 … G-9: deterministic generation, the clean-tree check, and detection of a hand edit, a tampered digest and an orphan artifact.
- P-1 … P-5: the provenance block is complete, the digest is reproducible by a third party, and no artifact carries a timestamp or an absolute path.
- M-1 … M-11: `contracts.toml` describes exactly the contracts that exist, in both directions.
- F-1 … F-6: every generated schema is valid draft 2020-12, every `valid/` fixture passes both layers and is byte-canonical, and every `invalid/` fixture is rejected by exactly the layers it declares.

Command surface: `cargo contracts generate`, `cargo contracts check`, `cargo test --workspace --locked`, `git diff --exit-code`.
